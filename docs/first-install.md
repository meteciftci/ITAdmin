# ITAdmin — first installation

The exact steps to install ITAdmin on a clean Windows Server 2022 or Windows Server 2025.

There is no release package, no version tag, and no deploy key: the repository is public, and the
server clones and builds it directly. For the architecture behind this, see
[deployment.md](deployment.md).

---

## Part 1 — Server prerequisites

Install these once, in an **elevated PowerShell** session:

1. **[Git for Windows](https://git-scm.com/download/win)** — accept the defaults.
2. **[.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0)** — the full SDK, not just
   the ASP.NET Core runtime; the server builds the backend itself.
3. **[Node.js 20+ (LTS)](https://nodejs.org/)** — ships with npm; the server builds the frontend
   itself.
4. **IIS** with the required Windows features. `Deploy-ITAdmin.ps1 -InstallIisFeatures` installs
   them if missing.
5. **[ASP.NET Core 10 Hosting Bundle](https://dotnet.microsoft.com/download/dotnet/10.0)** —
   ASP.NET Core Runtime → Hosting Bundle. Install this **after** IIS; if it was installed first,
   repair it.

Close and reopen PowerShell after installing so `PATH` is refreshed, then confirm:

```powershell
git --version
dotnet --list-sdks
node --version
```

ITAdmin never downloads or executes a prerequisite installer on your behalf; each of the above is a
manual, official-source install.

## Part 2 — Database precondition

PostgreSQL must already be running and reachable from this server. That is the whole precondition —
`Deploy-ITAdmin.ps1` creates its own database and its own least-privilege login role.

At install time you supply:

- **PostgreSQL user** — the name of the login role ITAdmin runs as (for example `itadmin_app`). It
  is created if it does not exist. Its password is **generated by the script**, stored only in the
  DPAPI machine secret store, and printed once at the end of the run — record it then.
- **PostgreSQL administrator user / password** — a superuser, or a role with `CREATEROLE` and
  `CREATEDB`. Used only to run `CREATE ROLE` / `CREATE DATABASE` and the schema grants. It is
  written to an ACL-restricted file that is deleted immediately after use, is never stored, and
  never reaches runtime configuration. The application never runs with this credential.

Under the covers this runs `ITAdmin.Api.exe --provision-database --input <file>` before any other
machine change. It is idempotent: re-running converges rather than erroring. To manage the
application role's password outside the script, pass `-DatabasePassword` and it is set to that
value instead of being generated.

## Part 3 — Install

```powershell
git clone https://github.com/meteciftci/ITAdmin.git C:\ITAdmin\src
C:\ITAdmin\src\scripts\deploy\Deploy-ITAdmin.ps1 -InstallIisFeatures
```

That is the canonical install command. `-InstallIisFeatures` is only needed the first time (or
after a Windows feature was removed); a run that finds them already present is a no-op for that
step.

### What it does

| Step | Detail |
| --- | --- |
| 1 | Preflight: OS, Git, .NET SDK, Node/npm, IIS features, ASP.NET Core Hosting Bundle |
| 2 | Prompts for the database target, a transient PostgreSQL administrator credential, the directory, and the first administrator |
| 3 | Clones the repository into `<InstallRoot>\src` |
| 4 | Builds the backend (`dotnet publish`) and the frontend (`npm ci && npm run build`) into `<InstallRoot>\app\<commit>` |
| 5 | Provisions the database and the application role |
| 6 | Generates the JWT signing key, the first-run setup key, and (unless supplied) the database role's password — all DPAPI-protected |
| 7 | Applies migrations |
| 8 | Establishes the Primary Directory and the initial administrator (`--bootstrap-directory` — there is no in-application setup wizard) |
| 9 | Points IIS at the new build and activates |
| 10 | Health-checks `/health` and `/api/setup/status`; on failure, reverts IIS to the previous build |
| 11 | Installs the ITAdmin Host Agent (and Update Coordinator) so **Settings → Updates** works later |
| 12 | Prints the summary, including the generated database password **once** |

### The prompts

```
PostgreSQL host
PostgreSQL database name
PostgreSQL user                                    (the application login role; created if absent)
PostgreSQL administrator user                       (used only to create the database and role)
PostgreSQL administrator password for '<admin>'     (no echo)
Directory host                                      (AD domain or a specific controller)
Directory Base DN                                   (e.g. DC=corp,DC=example,DC=com)
Directory bind account
Password for '<bind account>'                       (no echo)
Initial ITAdmin administrator                       (UPN, sAMAccountName, or email)
HTTP host header                                    (optional - Enter leaves it blank)
```

Passwords are read as secure strings and are not echoed. The application role's own database
password is not asked for — it is generated and shown once in the final summary (only when the
script generated it, i.e. you did not pass `-DatabasePassword`). Record it: the DPAPI secret store
does not travel to another host, so a bare-metal restore needs that value.

### Useful modes

```powershell
.\Deploy-ITAdmin.ps1 -WhatIfPreflightOnly       # validate configuration, change nothing
.\Deploy-ITAdmin.ps1 -InstallIisFeatures        # install missing IIS Windows features first
.\Deploy-ITAdmin.ps1 -HttpPort 8080             # non-default HTTP port
.\Deploy-ITAdmin.ps1 -HttpHostHeader itadmin.example.com
.\Deploy-ITAdmin.ps1 -Branch release            # track a branch other than main
```

## Part 4 — Expected result

A successful run ends with a summary similar to:

```text
ITAdmin deployment completed successfully.

  Source            a1b2c3d - feat: add license renewal reminders
  Branch            main
  Web (HTTP)        http://server-name/
  Database          db.example.com:5432/itadmin
  Schema            current
  IIS               site ITAdmin, app pool ITAdmin
  Active build      C:\ITAdmin\app\a1b2c3d
  Config            C:\ProgramData\ITAdmin\config\app.json
  Secrets           C:\ProgramData\ITAdmin\secrets  (Windows DPAPI LocalMachine)
  State             C:\ProgramData\ITAdmin\state\deploy.json

  Next: open http://server-name/ and sign in with the initial administrator's directory credentials.
        Configure HTTPS later with:  .\Deploy-ITAdmin.ps1 -ConfigureHttps

  ----------------------------------------------------------------------
  SHOWN ONCE - RECORD THIS NOW
  ----------------------------------------------------------------------
    Database role       itadmin_app
    Database password   <32-char generated value>
    ... stored in the DPAPI secret store above; not written to any log;
    will not be shown again.
  ----------------------------------------------------------------------
```

The one-time password block appears only when the script generated the application role's password
(not when you passed `-DatabasePassword`). Record it in your database and backup runbooks.

Open the printed URL and sign in with the initial administrator's **directory** credentials.

> **HTTP traffic is not encrypted.** Initial installation is HTTP-only by design so that reaching a
> working ITAdmin does not depend on a certificate being ready yet. Configure HTTPS afterwards:
>
> ```powershell
> .\Deploy-ITAdmin.ps1 -ConfigureHttps -CertificateThumbprint <40-hex-thumbprint> -RedirectHttpToHttps
> ```
>
> The certificate must already be installed in `Cert:\LocalMachine\My`. Treat the HTTP-only window
> as a commissioning state, not a steady state.

## Part 5 — Updating

Push to `main`, then re-run the exact same command on the server:

```powershell
C:\ITAdmin\src\scripts\deploy\Deploy-ITAdmin.ps1
```

It fetches the branch tip, rebuilds, migrates, and re-activates. The previous build stays on disk;
`-Rollback` points IIS back at it (database migrations are **not** reversed). The same update can
also be triggered from **Settings → Updates** in the app, which asks the ITAdmin Host Agent to run
this same script on the server.

## Repository governance (for the repository owner, not the server)

Because there is no release tag or artifact, the delivered code **is** whatever commit `main`
points at when a server pulls it. Protect `main` accordingly:

- Require pull request review (or at minimum, disallow direct force-push) on `main`.
- Rely on CI (`.github/workflows/ci.yml`) passing before merging — it builds, tests, and lints both
  the backend and the frontend on every push.
- A server only ever fetches what is currently on the branch tip; there is nothing to "publish"
  beyond pushing to `main`.
